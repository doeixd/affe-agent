# Review, fourth pass — design, duplication, and what is outside the gates

Follows passes [one](./review-2026-08-24.md), [two](./review-2026-08-24-2.md)
and [three](./review-2026-08-24-3.md), which covered correctness, concurrency
and adversarial input. This pass looks at shape: duplication, dead weight,
abstractions that did not earn themselves, and reasoning written twice.

Three of the five findings are about my own work. That is not modesty — the
audit changes touched four files with the same edit, and that is exactly where
this kind of problem grows.

---

## 1. The same error helper, written four times, populating different fields — **mine**

**Severity: medium (an inconsistent public error), scope: one shared function.**

`StorageError` was introduced with a structured `sessionId` field so a consumer
could filter on it. Four stores construct it, each through its own private
`storage(...)` helper:

| File | Helper | Fills `sessionId`? |
|---|---|---|
| `durable/DurableSessionStore.ts:605` | `storage(operation, sessionId?)` | yes |
| `durable/DeliveryLog.ts:239` | `storage(operation, sessionId?)` | yes |
| `durable/DurableChannels.ts:302` | `storage(operation, key?)` | **no** — folded into `detail` |
| `state/AgentState.ts:195` | `storage(operation, key)` | **no** — folded into `detail` |

The first two are byte-identical. The other two differ only in where the
identifier goes — and that difference is the defect. **`StorageError.sessionId`
is populated by half the stores**, so a caller writing

```ts
Effect.catchTag("StorageError", (e) => e.sessionId === mine ? retry : fail)
```

works against the session store and the delivery log, and silently never matches
for channels or state. A structured field that is only sometimes structured is
worse than no field, because it invites exactly that code.

`tree/NodeStore.ts:240` has a fifth copy under a different name (`fail`), which
is how you can tell the shape is missing rather than local: two authors reached
for it independently.

**Suggested fix.** One exported helper beside `StorageError` in `Errors.ts`:

```ts
export const storageFailure = (operation: string, id?: string) =>
  <A, E>(effect: Effect.Effect<A, E>): Effect.Effect<A, StorageError> => ...
```

Five call sites collapse to five imports, and `sessionId` gets filled the same
way everywhere. **Rename the field while doing it** — `sessionId` is wrong for
`AgentState`, whose key is `plan:user-42`, and for `DurableChannels`, whose key
is a channel. `id` says what it is.

**Missing test.** Nothing asserts the field is populated. One test per store —
force a failure, assert `error.id` is the key you passed — would have caught
this the day it was written.

## 2. `apps/tui` is outside every gate the repository has

**Severity: medium (it will rot), scope: config.**

2,076 lines of first-party TUI code, and:

- `tsconfig.json` has `"include": ["src", "test", "examples"]` — **`apps` is not
  in it**, so `npm run typecheck` and `npm run lint` never see it.
- `npm run check` runs those two plus portability (which scans `src/`) and
  vitest. There is no `vitest.config`, and the TUI has no `*.test.ts`, so the
  test run does not reach it either.
- CI has no reference to `apps` or `tui`.

It does compile today — `cd apps/tui && npx tsc --noEmit` exits clean, so
somebody is running it by hand. Nothing keeps that true. The first change to
`AgentSession`'s API that breaks the TUI will be found by whoever next opens it,
not by the build that made the change.

That matters more than usual here because the TUI is the *driving use case* for
the session tree: `plan-session-tree.md` justifies T1–T5 by what a renderer
needs. A consumer that CI cannot see is a consumer whose requirements silently
stop being checked.

**Suggested fix.** Add `apps/tui/typecheck` to `check`, or a project reference.
The cheap version is one line in `package.json`:

```json
"check": "npm run typecheck && npm run lint && npm run lint:portability && npm run test && npm --prefix apps/tui run typecheck"
```

## 3. `apps/tui/vendor/opencode/` is 4,865 lines nothing imports

**Severity: low-medium (weight and licence surface), scope: a decision.**

Ten files, 4,865 lines of third-party code, referenced **only from comments** —
every mention in `apps/tui/src/` is prose saying "the pristine copy is in
`vendor/`". No import statement anywhere reaches it.

It is more than twice the size of the TUI it accompanies. It is not compiled,
not linted, not tested, and cannot drift-detect against upstream because nothing
compares them. And it carries MIT attribution obligations for code the product
does not use.

The intent is legible and reasonable — keeping the original beside the port so a
future reader can diff the two, which is the same instinct as pinning the
upstream commit in `plan-opencode-tools-port.md`. But a directory is a poor
diff: nothing detects when the port and the pristine copy diverge, which is the
only thing it is for.

**Suggested fix**, in order of preference:

1. **Delete it and pin the commit.** `plan-tui-port.md` already records the
   upstream and its commit; that is a *better* reference than a stale copy,
   because `git clone --depth 1` at that commit reconstructs it exactly.
2. Keep it, and add a check that fails when a vendored file changes without its
   ported counterpart being touched — which is what the directory implies but
   does not do.

## 4. `unstable/persistence` is now adopted in exactly one place — **half a migration**

**Severity: medium (two idioms for one job), scope: a decision, not code.**

Audit E3 found two hand-rolled `interface Store` key-value seams and recommended
`effect/unstable/persistence`. `tree/NodeStore.ts` adopted it — correctly, and
its commit message says so. Nothing else moved:

| | Seam |
|---|---|
| `unstable/persistence` | `tree/NodeStore.ts` |
| Hand-rolled `interface Store` | `durable/DurableChannels.ts:34`, `state/AgentState.ts:151` |

So the codebase now has **both** idioms, which is the one outcome E3 was written
to avoid. A reader adding a third store has two precedents and no rule. Worse,
audit invariant **A1** says *"adoption must delete code — adding an ecosystem
module alongside the thing it was meant to replace is a net loss"*, and that is
precisely the current state.

**Suggested fix.** Either migrate the other two to `KeyValueStore` and delete the
hand-rolled interfaces, or record in the audit why the new one is different and
the old ones stay. Both are fine; having neither written down is not.

Note this interacts with pass two's finding: `NodeStore`'s read-then-write race
exists *because* `KeyValueStore` offers no atomic update. That is a real argument
against blanket migration, and it belongs in the decision.

## 5. Reasoning written twice — **mine**

**Severity: low (maintenance), scope: judgement.**

`internal/schedules.ts` is 87 lines: **19 of code and 68 of comment (78%)**. The
module exports two functions and a constant.

Some of that earns its place — the note that `Schedule.jittered` multiplies by
`[0.8, 1.2]`, so a cap applied before it is not a cap, encodes a real bug the
tests caught and belongs exactly there. But the surrounding essay on thundering
herds is the same argument, in my own words, that `audit-effect-ecosystem.md`
E16 already makes at length.

This repository has a convention worth honouring: `PLAN.md` and `STATUS.md` hold
*why the design is this*, and code comments hold *why this line*. I put a design
essay in both places, so the two can now disagree.

**Suggested fix.** Trim the module to the line-level facts — the jitter range,
the ordering, why `steady` is not exponential — and point at E16 for the
argument. `internal/detail.ts` (12 lines, 7 of comment, for a four-line
function) is the same shape at a size where it does not matter.

**A related one-liner:** `Observability.defaultSpanRedaction` is exported and
referenced by no file but its own. It is the documented default of
`redactingTracer`, so it is not dead — but nothing exercises it by name, and an
exported constant with no test and no example is a maintenance liability rather
than an API.

## Not findings, recorded so they are not re-raised

**The comment density elsewhere is a feature, not slop.** `lineEndings.ts` at
59% and `searchFormat.ts` at 43% are explaining ported decisions and upstream
thresholds — the comments carry information the code cannot. The contrast with
finding 5 is the point: those comments say *why this constant is 0.65*; mine
said *why fixed-interval retry is bad in general*, which belongs upstairs.

**`WebFetch.ts` at 7% comment is not under-documented.** It is mostly Schema
definitions and error classes, where the names are the documentation.

**The TUI's own code compiles and is structured sensibly** — `store.ts`,
`view.ts` and `width.ts` are small and single-purpose, and `harness.ts` carries
the Effect boundary. The finding above is about the gates around it, not its
quality.

## Suggested order

1. **One `storageFailure` helper, and fill the id everywhere** (finding 1) —
   it is a public error behaving inconsistently, and the fix deletes code.
2. **Put `apps/tui` in `check`** (finding 2) — one line, and it stops a
   consumer silently rotting.
3. **Decide about `vendor/`** (finding 3) and **about the two store idioms**
   (finding 4). Both are decisions to record, not code to write.
4. **Trim `schedules.ts`** (finding 5) when next in the file.

## Across four passes

Pass one found signatures that lie, pass two a demonstrated race, pass three a
demonstrated denial of service, and this one duplication and dead weight. The
through-line is consistent: **the code is careful and the scaffolding around it
is not** — tests that do not exercise adversarial input, gates that do not cover
a whole app, an error type populated by half its callers, an ecosystem module
adopted in one place.

None of that is a criticism of the code's design, which is unusually
well-reasoned throughout. It is the ordinary consequence of a lot of ground
covered quickly, and all of it is cheaper to fix now than after the next
thousand lines.
