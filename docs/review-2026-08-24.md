# Review: today's changes

Covers `af8e62c..HEAD` — 111 files, ~22,900 insertions. Two workstreams on one
branch: the ecosystem audit (`audit(effect)`, `feat(agent)`) and the

## Summary

The tree is in good shape: `npm run check` is green, 906 tests, zero Effect
diagnostics, portability passing without the Slack exemption. The new code is
better commented than most of what it sits beside, and two of the riskiest
pieces — the fetch guard and the tree's activation race — are visibly the work

Findings are ordered by what I would fix first.

## 1. `Agent.run` and every other entry point ignore `withExecutionPlan` — **mine**

**Severity: high (a signature that lies), scope: small fix.**

A-3 threads a `Model` type parameter so a planned agent stops requiring
`LanguageModel`. It reaches `AgentSession.make` and `restore` and **nothing
else**. `Agent.run` — the documented one-shot, and the first thing a new user
touches — still reads:

```ts
export const run = <Tools, E, R>(
  agent: AgentDefinition<Tools, E, R>,   // Model defaults to LanguageModel
  ...
): Effect.Effect<..., LanguageModel.LanguageModel | R>
```

Because `Model` is phantom (it appears in no field), a planned agent is still
*assignable*, so this compiles and silently demands a model that will never be
consulted. Verified with a scratch assertion:

```ts
export const probe = Agent.run(planned, "go")
type ProbeR = typeof probe extends Effect.Effect<any, any, infer R> ? R : never
type _ = Assert<[ProbeR] extends [never] ? true : false>
// => error TS2344: Type 'false' does not satisfy the constraint 'true'
```

That is precisely the "lie the signature should not tell" the change was
written to remove — it just moved from `make` to everything around it.

Same shape, unverified but near-certain by inspection: `AgentClient.layer`
(`client/AgentClient.ts:330`), `SessionTree.make` (`tree/SessionTree.ts:405`),
`Subagent.tool`, `DurableAgentClient.layer`, `Scheduling`.

**Suggested fix.** Thread `Model` through every function whose parameter is an
`AgentDefinition`, exactly as `make` does. It is mechanical — the parameter is
defaulted, so no call site moves.

**Missing test, and it is the important part.** The X4 example asserts `R` is
`never` for `AgentSession.make` only. Add the same assertion per entry point;
that turns a family of silent gaps into a compile error. Without it this
regresses the next time an entry point is added.

## 2. The fetch guard's manual-redirect guarantee depends on the injected client

**Severity: medium-high (security), scope: docs or a guard.**

`web/http.ts` is otherwise the best-defended code in the diff. It refuses
non-http schemes, embedded credentials, localhost/`.local`/metadata hostnames,
every private and reserved IPv4 range, IPv6 loopback/ULA/link-local/site-local/
multicast, and IPv4-mapped IPv6 — then **re-validates every redirect target**
and refuses cross-origin redirects outright, which is stronger than most
libraries manage.

All of that rests on one line:

```ts
Effect.provideService(FetchHttpClient.RequestInit, { redirect: "manual", credentials: "omit" })
```

`make` takes an abstract `HttpClient.HttpClient`. A client that is not
`FetchHttpClient` ignores `RequestInit` — so a custom or wrapped client that
follows redirects internally silently defeats `validateTarget` on every hop
after the first. The seam that makes this package portable and testable is also
the seam that can disarm it.

**Suggested fix**, in order of preference:

1. State the requirement in `make`'s doc comment: *the supplied client must not
   follow redirects*. Cheapest, and it makes the contract reviewable.
2. Detect it: if a response arrives with a 2xx status and a `url` that differs
   from the request's, the client followed something. Fail loudly.

**Missing test.** No test supplies a redirect-following client and asserts the
outcome. Today that behaviour is undefined, and undefined is the wrong state for
a control whose whole purpose is refusing to reach a private address.

## 3. SSRF denial table tests less than the code denies

**Severity: medium (regression risk), scope: one table.**

`test/HttpWebFetch.test.ts` has 15 denial cases and they are well chosen —
including `2130706433`, the decimal form. But `http.ts` denies strictly more
than the table covers, so a regression in the untested branches is silent:

| Denied in code | In the test table |
|---|---|
| `0.0.0.0` (`first === 0`) | no |
| `100.64.0.1` (CGNAT) | no |
| `198.18.0.1` (benchmark) | no |
| `224.0.0.1`, `255.255.255.255` (`first >= 224`) | no |
| `[fec0::1]` (site-local) | no |
| `[ff02::1]` (multicast) | no |
| `http://127.0.0.1./` (trailing dot) | no |
| `http://LOCALHOST/` (case) | no |

The last two matter most: `normalizedHostname` strips trailing dots and
lowercases, and both are classic bypasses. The code handles them; nothing
proves it keeps handling them.

**A non-finding worth recording.** I expected `http://0177.0.0.1/` (octal) to
bypass the guard, because `Number("0177")` is `177`, not `127`, and
`inet_aton` reads leading zeros as octal. It does not: the WHATWG `URL` parser
normalises octal and decimal forms *before* `hostname` is read, so the guard
sees `127.0.0.1`. Verified:

```
new URL("http://0177.0.0.1/x").hostname   // => "127.0.0.1"
new URL("http://2130706433/x").hostname   // => "127.0.0.1"
```

The safety is real but it belongs to the URL parser, not to this code. The
existing `2130706433` case pins half of it; **add `0177.0.0.1` for the other
half**, so a future move to hand-rolled parsing fails loudly.

## 4. `redactingTracer` filters `attribute` but its `event` path is untested — **mine**

**Severity: low-medium, scope: one test.**

`Observability.redactingTracer` drops named keys from both `span.attribute(...)`
and `span.event(name, time, attributes)`. Only the first is tested. Effect AI
happens to annotate rather than emit events today, so the gap is latent — but
the code is there and the leak it closes is a privacy one, which is not the
place to carry untested branches.

**Suggested test.** Call `span.event("x", 0n, { parameters: "secret" })` through
the wrapper and assert the attribute is gone. Small, and it makes the second
half of the function real.

## 5. `internal/schedules.ts` is tested as a schedule, not at its call sites — **mine**

**Severity: low, scope: judgement.**

`test/Schedules.test.ts` asserts the delays `steady` and `backoff` produce —
correct, and it caught a real bug (jitter can exceed a cap, so the cap must come
last). What it does not assert is that the four call sites actually use them.
Reverting `EntityClient` to `Schedule.spaced` would leave the suite green.

**Suggested fix.** Either accept it and say so, or pin the wiring the way
`Casts.test.ts` pins the cast inventory — a test that greps `src/` for
`Schedule.spaced(` outside `internal/schedules.ts` and fails. The second is
cheap and matches a technique this repo already trusts.

## 6. Three process-spawning tests are intermittently flaky

**Severity: unknown, and that is the problem.**

Across today's full-suite runs, three tests each failed exactly once and passed
in isolation and in every subsequent run:

- `WebDurable.test.ts > replay does not repeat a completed fetch provider call`
- `McpStdioCompatibility.test.ts > negotiates modern stdio, propagates interruption, and cleans up`
- `Sandbox.test.ts > a descendant holding the pipes cannot keep a finished command open`

All three spawn processes, which points at contention under full-suite load
rather than a defect. But the first asserts **D2 — resumption never repeats
completed work** — and a flaky test on a durability invariant is worse than a
failing one, because it teaches people to re-run.

**Suggested action.** Run the suite with `--repeat` on those three files and
either find the race or record the contention as known. Do not leave it as
folklore.

## 7. Smaller notes

**`deniedIpv4` omits documentation ranges.** `192.0.2.0/24`, `198.51.100.0/24`,
`203.0.113.0/24` and `192.0.0.0/24` are reserved and reachable-looking. Not a
security hole — they route nowhere useful — but adding them is two lines and
makes the list match its intent.

**`fetchOne` validates `next` twice.** `validateTarget(next)` runs before the
recursive call, which then runs `validateTarget(current)` on the same URL.
Harmless and arguably good defence in depth; worth a comment saying it is
deliberate, or the next reader will "simplify" one away.

**`AgentState`'s phantom error is undocumented at the use site.** Ephemeral
state now declares `StorageError` on its mutations and can never raise it. The
reasoning is in the module and in the audit, but a caller meeting
`Effect.orDie` in `test/AgentState.test.ts` has no pointer. One line in the
`layer` doc comment would close it.

**`recordAttempt` attributes by `String(stepIndex)`.** Cardinality is bounded by
plan length, so this is fine — noted only because metric label cardinality is
the usual way a counter becomes a bill.

## What I checked and found sound

Recorded so it is not re-reviewed:

- **The tree's activation race.** `SessionTree` guards switching with a
  semaphore, and the comment explains the exact failure it prevents — two
  concurrent rewinds both closing one predecessor, leaving the loser's scope
  forwarding into the feed. It also adopts `RcMap` for branch lifetimes, which
  is the audit's E4 recommendation landing in the place it was written for.
- **The coding toolkit's lock registry.** `TxRef` + holder count; drain and
  evict are one commit. Three tests including the one the old comment said
  could not be written.
- **The redirect policy.** Manual redirects, re-validation per hop,
  cross-origin refusal, a hop limit, and `credentials: "omit"`.
- **`Tracer.Span` delegation.** The wrapper covers every member; TypeScript
  caught the one I missed (`addLinks`) rather than it shipping as a hole.
- **Storage error triage.** Four seams keep `orDie` with the argument written
  down at the site, each a core interface that declares no error.

## Suggested order

1. Thread `Model` through the remaining entry points (**1**) — a signature that
   lies is worse than a missing feature, and the fix is mechanical.
2. Document or detect the redirect-following client (**2**).
3. Extend the SSRF table (**3**) and add the `event` redaction test (**4**).
4. Decide about the flaky three (**6**) rather than watching them.
5. The rest is polish.
