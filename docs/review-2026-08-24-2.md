# Review, second pass

Follows [review-2026-08-24.md](./review-2026-08-24.md), which covered the fetch
guard, `Agent.run`'s missing `Model` threading, and the test-coverage gaps
around them. This pass went into the code that review did not reach: the
replacer chain, the tree's new persistence (`a7c4b9e`, landed after the first
report), the web toolkit's permission surface, and the storage work.

One finding is serious and demonstrated. The rest is smaller.

---

## 1. `NodeStore` loses siblings on any backing that yields — **demonstrated**

**Severity: high (silent data loss), scope: two functions.**

`NodeStore.keyValue`'s index maintenance is read-then-write:

```ts
const append = (key: string, id: string) =>
  readIds(key).pipe(                                   // read
    Effect.flatMap((existing) =>
      existing.includes(id)
        ? Effect.void
        : ids.set(key, [...existing, id])))             // write
```

Two concurrent `put`s under one parent both read the same index and both write
their own successor. One child is lost — **from the index only**. The node
itself was written first (deliberately, and the comment explaining that ordering
is good), so `get(id)` still finds it. It is simply no longer anybody's child.
Nothing fails, nothing logs, and the tree is quietly wrong.

**Why the tests do not catch it.** `NodeStore.test.ts` builds the store over
`KeyValueStore.layerMemory`, which is a synchronous `Map` — `get` and `set`
never suspend, so the two steps are effectively atomic and the race cannot
occur. The file says so, and states the claim that makes this matter:

> the key-value store is built over `layerMemory` here rather than a real
> backing: what is under test is the *adapter* … and that is the same code
> whether the map is in memory, on disk, or in Postgres.

The adapter is the same code; the *concurrency* is not. Every real backing —
SQL, Redis, a file, anything over a socket — suspends between `get` and `set`.

**Demonstrated.** Wrapping `layerMemory` so its operations yield, which is all
any real store does:

```ts
get: (key) => Effect.andThen(Effect.yieldNow, kv.get(key)),
set: (key, value) => Effect.andThen(Effect.yieldNow, kv.set(key, value))
```

then storing twelve siblings concurrently:

```
YIELDING KV -> kept 1 of 12
```

**Eleven of twelve nodes disappeared from `children()`.**

The same shape is in `NodeStore.memory`:

```ts
const existed = (yield* Ref.get(held)).has(node.id)   // read
yield* Ref.update(held, ...)                           // write
if (!existed) yield* Ref.update(order, ...)            // write derived from the read
```

That one I could *not* demonstrate — `Ref` operations do not suspend, so the
window never opened in practice. It is the same latent shape and the same fix,
but I am not claiming it loses data today.

This is the pattern AGENTS.md names explicitly: *"State transitions that guard
an invariant must be atomic. `SubscriptionRef.modify`, not read-then-write:
correctness must not depend on where the runtime happens to yield."* It is also
the fourth time this codebase has met it — after the coding toolkit's lock
registry, `DurableSessionStore.claim`, and `AgentState`'s swap-and-persist.

**Suggested fix.** The index write needs to be atomic *at the store*, and a
`KeyValueStore` cannot offer that — which is the real finding underneath the
bug. Options, in order of preference:

1. **Serialise `put` behind a `Semaphore`** held for the whole
   read-modify-write. One line, correct within a process, and honest about its
   limit: it does not help two processes sharing a backing. Given `SessionTree`
   is a single-process construct today, this is proportionate.
2. **Key each child individually** — `children/{parent}/{childId} -> ""` — so
   there is no shared list to lose. Ordering then needs a sequence number in
   the key, which the store already has via its counter. Slower to read,
   correct without coordination, and works across processes.
3. Document the store as single-writer, and say so on `NodeStore` rather than
   in a commit message.

**Missing test, and it is the point.** `NodeStoreContract.ts` has eight tests
and none of them is concurrent — including
`"re-storing an id replaces the node without duplicating it"`, which is exactly
the invariant the race breaks. **Add a yielding backing to the contract** and
run both implementations against it. The technique is already in this
repository: `CodingToolkit.test.ts` wraps the sandbox to force a yield between
read and write, and that is how its lost-update test was written.

## 2. The conformance suite proves behaviour, not atomicity

**Severity: medium (process), scope: one helper.**

Generalising finding 1. This repository has three separate places where a
read-then-write bug was found and fixed, and the fix in each case came with a
test that forced the interleaving. The newest store shipped with a conformance
suite that is careful, well-written, and entirely sequential.

**Suggestion.** Make "run the contract against a yielding backing" a standard
row in every store contract — `DeliveryLogContract`, `AgentClientContract`, and
now `NodeStoreContract`. It costs one wrapper and it is the only cheap way to
stop this class recurring, which on the current evidence it does about once a
month.

## 3. `SessionTree` will call `put` concurrently by design

**Severity: contextual — it is what makes finding 1 reachable.**

The tree auto-captures on `TurnCompleted`, and `plan-session-tree.md` keeps
concurrent branches explicitly possible ("they are opt-in, not the model").
Two live branches capturing turns are two fibres calling `store.put` with the
same parent. That is the exact shape above.

Worth stating in the plan's T5 section: **the store's write path is the
serialisation point**, and until it is, concurrent branches and persistence
should not be recommended together.

## 4. Web toolkit and Brave client — checked, and sound

Recorded because I went looking for problems and did not find them:

- **Permission projections are present and well chosen.** `Search` projects to
  `net.search` on the *query*; `Fetch` projects to `net.fetch` on the
  **canonical origin**, not the full URL. Projecting on origin is the right
  granularity — a policy that allowed `https://api.example.com/a` and denied
  `/b` would be security theatre, since the path is attacker-influenced.
- **The API key is `Redacted`,** and `Headers.CurrentRedactedNames` is updated
  so the key does not surface in logged request headers.
- **Responses are size-capped** (`MAX_RESPONSE_BYTES`) on both the search and
  fetch paths, and the result count is clamped with
  `Math.min(..., Math.max(1, Math.trunc(...)))` — so a hostile or careless
  `limit` cannot become an unbounded read.

## 5. The replacer chain's safety property holds

Also checked and sound, and worth recording because it is the code most capable
of silent damage.

`replace` verifies every candidate with `content.indexOf(candidate)` before
using it, and splices by index:

```ts
const index = content.indexOf(candidate)
if (index === -1) continue   // a strategy may only point at text that is really there
```

That enforces I1 — *select, never synthesize* — **by construction** rather than
by each of nine strategies being careful. A strategy could return arbitrary
text and the driver would refuse it. That is the right place for the check.

One observation, considered and not a finding: `isDisproportionate` exempts
single-line finds from its length check, so a three-character find can replace
a very long line if the two are whitespace-equal. That is what
whitespace-normalized matching is *for* — the guard exists to catch a match
that swallowed unrelated content, and whitespace is not content. Leaving it
alone is right; the exemption deserves the one-line comment it already has.

## 6. Smaller notes

**`nodesOf` fails the whole read on one torn entry.** If the index names a node
that is not stored, the store fails rather than returning the rest — deliberate,
and the comment says why ("reporting it as a gap would hide the damage"). Worth
knowing that this makes a single torn write disable `children()` for that parent
entirely. Given finding 1 can *produce* index/entry divergence, these two
interact: the fix for 1 also reduces the blast radius here.

**`NodeStore<E>` is generic in its error, which is right** — and worth calling
out as the E14 lesson being applied rather than re-learned. The persisted
implementation names `StoreError`; the memory one is `never`. That is what the
storage triage was trying to establish as normal.

**The tree's activation semaphore is correct and its comment is the best in the
diff** — it names the failure it prevents (two concurrent rewinds both closing
one predecessor, the loser's scope still forwarding into the feed) and where it
comes from (a held Ctrl+R). Contrast with finding 1: the same author reasoned
carefully about concurrency one file away. The gap is not skill, it is that the
store *looked* like plumbing.

---

## Suggested order

1. **Serialise `NodeStore.put`** (finding 1). One semaphore, and the tree stops
   losing branches on any real backing.
2. **Add a yielding backing to `NodeStoreContract`** — this is what turns the
   fix into something that stays fixed, and it is the same helper the coding
   toolkit already uses.
3. Generalise that helper to the other store contracts (finding 2).
4. Note the single-writer constraint in `plan-session-tree.md` T5 until 1 lands.

Findings 4, 5 and 6 need no action; they are recorded so the same ground is not
re-covered.
