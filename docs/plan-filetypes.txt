Not completely. The **core is already multimodal in the right way**, but I would not call effect-agent end-to-end multimodal yet.

The good news is we do **not** need a new image system. Effect AI already gives us the correct typed primitive: `Prompt.FilePart`. It represents images, PDFs, and other files with `mediaType`, optional `fileName`, and data as a string, `Uint8Array`, or `URL`.  Effect's response model likewise has a first-class `FilePart`, including in streaming responses.

The gaps are mostly in **wire encoding, large-object storage, and protocol projections**.

### Local core is actually quite good

This already works conceptually:

```ts
const image = Prompt.filePart({
  mediaType: "image/png",
  fileName: "screenshot.png",
  data: bytes
})

yield* session.prompt([
  Prompt.textPart({
    text: "What's wrong with this UI?"
  }),
  image
])
```

`AgentSession.prompt` accepts `Prompt.RawInput`, and the remote protocol
normalizes inputs to `Prompt.Prompt`. The canonical remote protocol uses
`PromptWire.Prompt` for `prompt`, `steer`, `followUp`, and history responses.
That codec's decoded type is still exactly `Prompt.Prompt`; only the stable
process-boundary representation differs.

That's the right foundation.

## Canonical history preserves multimodal output too

`AgentTurn` doesn't reduce a model response to text when committing it.

It does:

```ts
History.fromResponseParts(response.content)
```

and commits that complete prompt plus tool results atomically. So a provider-generated `Response.FilePart` can become part of canonical history.

That's important.

The architecture is:

```text
model response
  ├ text
  ├ reasoning
  ├ files/images
  ├ tool calls
  └ metadata
        ↓
History.fromResponseParts
        ↓
canonical Prompt
```

not:

```text
model response
        ↓
response.text
        ↓
canonical history
```

So we got that part right.

# Where it currently breaks down

The biggest immediate problem is the **observation/remote projection**.

`RemoteResult` deliberately returns only:

```ts
{
  submissionId,
  status,
  runs,
  turns,
  text
}
```

The comment explicitly says the full `GenerateTextResponse`, including typed content parts, is dropped at the remote boundary.

Similarly:

```ts
MessageCompleted {
  text: string
}
```

and streaming deltas only support:

```ts
kind: "text" | "reasoning"
```

even though Effect's stream itself may contain `FilePart`.

So right now this can happen:

```text
MODEL RETURNS
─────────────
text
image
file

        ↓

CANONICAL HISTORY
─────────────
text       ✅
image      ✅
file       ✅

        ↓

REMOTE RESULT / EVENTS
─────────────
text       ✅
image      ❌
file       ❌
```

That's the first thing I'd fix.

# A2A is definitely text-only today

The current A2A adapter explicitly iterates A2A message parts, accepts only:

```text
text
```

and rejects anything else as unsupported. Its response/artifact builder also creates text parts only.

So A2A currently cannot faithfully bridge:

```text
image
PDF
binary artifact
```

even though A2A itself has richer `Part` / `Artifact` concepts.

That's an adapter limitation, not a core limitation.

The current AG-UI adapter declares:

```ts

```

and even comments that it accepts the protocol's general shape before narrowing it to what the harness adapter can faithfully convert. Its outgoing event vocabulary is primarily text/tool oriented.

That's pragmatic, but not the endpoint we want.

For multimodal support, it should have explicit conversion cases rather than:

    ↓

# Durable storage still needs large-object work

The durable session store preserves canonical `Prompt.Prompt` through the
shared JSON-safe `PromptWire` codec. Before Phase 1 it did:

```ts
Schema.encodeEffect(Prompt.Prompt)(prompt)
    ↓
JSON.stringify(...)
```

and stores the resulting JSON string.

The first issue is now closed. Conformance tests cover every
`FilePart.data` runtime variant:

```text
string/base64
data URL
URL
Uint8Array
```

through:

```text
Prompt.Prompt
→ Schema.encode
→ JSON.stringify
→ JSON.parse
→ Schema.decode
```

`PromptWire` uses Effect's URL and base64 transformations, tags the runtime
variant explicitly, and validates the complete encoded value as `Schema.Json`.
New writes never rely on incidental `JSON.stringify(Uint8Array)` behaviour.
Legacy untagged strings remain readable as strings because rejecting existing
durable rows would be worse; the old encoding did not preserve enough
information to recover whether such a string began as bytes or a URL.

The remaining issue is independent of codec correctness:

> **Putting a 25 MB PNG as base64 inside the session-history SQL row is the wrong storage model.**

So we need a second phase.

# I would make this a dedicated multimodal hardening plan

The design principle should be:

> **Effect `Prompt.FilePart` remains the semantic media primitive. effect-agent adds only transport/storage semantics that Effect AI cannot know.**

Do not create:

```text
AgentImage
AgentDocument
AgentMedia
AgentFilePart
```

We already have those semantics through `Prompt.FilePart`.

## Phase 1 — make inline multimodality actually correct ✅

Implemented 2026-08-27. `src/PromptWire.ts` is public at the root namespace and
is used by HTTP, RPC, cluster entities, durable workflows and stores,
snapshots/exports (full and JSONL), and key-value session trees. Deterministic
tests cover malformed base64, legacy reads, all three variants, both wire
directions, real SQLite, and all current persistence/transport consumers.

Export format version 2 records the incompatible file-data representation, and
`Export.MINIMUM_READABLE_VERSION` is 1: a bump protects an old reader from a
new file, and is not a reason to refuse an old one. A v1 export with no file
part is byte-identical to a v2 one, and `FileDataWireRead` accepts the untagged
form v1 wrote, so there is nothing a v1 file needs that this build cannot give
it. The gate was briefly strict equality, which made every export written
before the rollout unopenable.

Corrected 2026-08-28: the per-consumer round-trips originally exercised only
the `Uint8Array` variant, so "all three variants" was true of `PromptWire`'s own
unit test and not of the boundaries. The HTTP and durable-store round-trips now
carry bytes, a `URL` and a string each. The URL case is the one worth pinning:
`FileDataWireRead` accepts a bare string on read, so a URL that failed to encode
as `{_tag:"Url"}` would come back as a *string* rather than as an error — and a
string is a legal `FilePart.data`, so nothing downstream would notice.

Add a transport codec, conceptually:

```ts
PromptWire
```

It is **not a new prompt type**.

It is a codec:

```text
Prompt.Prompt
     ↕
stable process-boundary representation
```

The only tricky portion is `FilePart.data`.

I would encode its runtime variant explicitly:

```ts
type FileDataWire =
  | {
      readonly _tag: "String"
      readonly value: string
    }

  | {
      readonly _tag: "Bytes"
      readonly base64: string
    }

  | {
      readonly _tag: "Url"
      readonly value: string
    }
```

Then:

```text
Prompt.FilePart
data: Uint8Array
        ↓
Bytes(base64)

Prompt.FilePart
data: URL
        ↓
Url(string)

Prompt.FilePart
data: string
        ↓
String(string)
```

On decode, we reconstruct the exact Effect type.

That means no ambiguity and no reliance on JavaScript's `JSON.stringify(Uint8Array)` behavior.

Use this codec everywhere a `Prompt` crosses a JSON/durable boundary:

```text
HTTP
RPC JSON serialization
DurableSessionStore
session export/import
relay mailbox
future Control API
```

For Effect RPC's binary protocol we can later optimize actual bytes, but **the semantic wire codec remains one definition**.

# Phase 2 — expose non-text output remotely

Change the remote result from:

```ts
RemoteResult {
  ...
  text
}
```

toward:

```ts
RemoteResult {
  ...
  text

  content:
    ReadonlyArray<RemoteContentPart>
}
```

But don't expose raw provider-specific `GenerateTextResponse`.

The existing decision to avoid that was correct.

Instead expose provider-neutral content.

Potentially the cleanest representation is simply the final assistant message's `Prompt.Part` representation:

```ts
content: Schema.Array(Prompt.Part)
```

through the new wire codec.

So:

```ts
const result =
  yield* remote.prompt(...)

result.text

for (const part of result.content) {
  switch (part.type) {
    case "text":
      ...
      break

    case "file":
      ...
      break
  }
}
```

fully discriminated and type-safe.

# Phase 5 — add a Blob/Artifact store

This is what makes the system serious.

Inline content is fine for:

```text
12 KB PNG
small PDF
tiny screenshots
```

It is bad for:

```text
50 MB video
20 MB PDF
500 screenshots
build artifacts
```

So add a narrow storage capability.

I'd call the infrastructure abstraction something boring like:

```ts
BlobStore
```

rather than `MediaManager`.

Something approximately:

```ts
interface BlobStore {
  put(
    content: Stream<Uint8Array>,
    metadata: BlobMetadata
  ): Effect<BlobRef, BlobError>

  get(
    ref: BlobRef
  ): Stream<Uint8Array, BlobError>

  stat(
    ref: BlobRef
  ): Effect<BlobInfo, BlobError>

  remove(
    ref: BlobRef
  ): Effect<void, BlobError>
}
```

with:

```ts
const BlobRef = Schema.Struct({
  id: BlobId,
  mediaType: Schema.String,
  byteLength: Schema.Number,
  sha256: Schema.String,
  fileName: Schema.optional(Schema.String)
})
```

Implementations later:

```text
memory
filesystem
S3/R2
object storage
```

This service doesn't know anything about agents.

# Then the wire can externalize large file parts

At the model-facing/runtime layer:

```ts
Prompt.FilePart {
  mediaType: "image/png",
  data: Uint8Array(...)
}
```

At a remote/durable boundary, the codec can choose:

```text
small file
  ↓
inline base64

large file
  ↓
BlobStore
  ↓
BlobRef
```

So the remote form becomes:

```ts
type WireFileData =
  | InlineString
  | InlineBytes
  | Url
  | BlobRef
```

Receiver resolves `BlobRef` when it actually needs the bytes.

This also solves the relay problem we were just discussing.

You do **not** want:

```text
30 MB image
  ↓
base64 (+33%)
  ↓
Relay RPC frame
  ↓
SQL history
  ↓
event stream
```

five times.

Instead:

```text
Desktop
   ↓
BlobStore.put(image)

BlobRef
   ↓
Relay
   ↓
Laptop

Laptop
   ↓ only if needed
BlobStore.get(ref)
```

# Content-addressing is particularly attractive

I'd make `BlobId` derive from content hash where practical:

```text
sha256(bytes)
```

Then the same screenshot sent three times naturally deduplicates.

And session history can safely refer to immutable content.

```text
BlobRef:
  hash = abc123
  mediaType = image/png
  size = 812321
```

The data never changes underneath historical conversation state.

That's exactly what we want.

# Security needs explicit rules

Files introduce some security boundaries we don't currently have to care much about with text.

I would require:

* Maximum inline bytes.
* Maximum accepted file bytes.
* MIME type allow/deny policy where appropriate.
* Never trust `fileName` as a filesystem path.
* Never automatically write attachments into a workspace using their supplied name.
* Remote URLs should **not automatically be fetched by the relay**.
* URL fetching should go through the appropriate network/sandbox capability.
* Blob references must be authorized by principal/session ownership.
* Signed blob URLs should be short-lived if used.
* Hash content when persisted.
* Do not execute files merely because the model received them.

And maintain the existing distinction:

```text
attachment availability
        ≠
agent permission to manipulate workspace
```

An uploaded image does not give the agent permission to write arbitrary files.

const input = Prompt.make([

const history =

attachment: any
