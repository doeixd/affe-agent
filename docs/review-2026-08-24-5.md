# Review, fifth pass — the record, the replay, and what happens on failure

Follows passes [one](./review-2026-08-24.md), [two](./review-2026-08-24-2.md),
[three](./review-2026-08-24-3.md) and [four](./review-2026-08-24-4.md).

Those covered correctness, concurrency, adversarial input, and shape. This pass
takes the angles none of them did: **what reaches the model**, **what happens
when a background operation fails**, and **whether the repository's own record
still describes the repository**.

Two findings are documentation being wrong rather than code being wrong, which
in a library whose docs carry this much of the design is not a lesser category.

---

## 1. `STATUS.md` no longer describes the repository

**Severity: medium (it is the stated record), scope: regenerate two numbers.**

`AGENTS.md` opens with: *"`PLAN.md` is the design authority; `STATUS.md` records
what is built and why."* Right now:

| `STATUS.md` says | Actually |
|---|---|
| `npm test` — **843 passing** | **961 passing** |
| **31** published entry points | **37** |

The entry-point count is the sharper one, because three whole packages shipped
today — `/tree`, `/export`, `/web` — and the document that is supposed to record
what is built does not mention that they exist. A reader trusting `STATUS.md`
would not know the session tree is reachable from outside the repository.

What makes this worth a finding rather than a chore is that the file **tells you
how to avoid it**:

> `verify:package` is the source of truth for the entry-point count; regenerate
> these numbers from `npm run verify:package` and `npm run test` when they
> change.

The instruction is there and was not followed — by either of us; I updated the
count twice today and stopped, and the three new packages landed after.

**Suggested fix.** The instruction is the problem: a number that must be
regenerated by hand will drift. Either drop the exact figures from the prose (a
reader does not need to know it is 961) or generate that line. `verify:package`
already computes the entry count; having it write the line is a small script and
removes the class.

## 2. `Replay`'s doc comment contradicts itself two sentences apart

**Severity: low, but precisely the kind of wrong that reads as authoritative.**

`src/export/Replay.ts`:

> - **CI that cannot flake**, because there is nothing non-deterministic left.
>
> The honest limit is written into `turnsOf` below: a replay reproduces what the
> *model* said, not what the *tools* did.

Both cannot be true. If the tools are not reproduced, then a replayed session
that ran `bash`, `search` or `web_fetch` runs them **for real** — against this
filesystem, this network, today. There is a great deal non-deterministic left;
it just is not the model.

The caveat is present and correct, which is why this is a small finding rather
than a missing-warning one like pass three's export redaction. But the sentence
above it will be the one a reader quotes.

**Suggested fix.** "CI with no *provider* non-determinism, and no cost" — then
the caveat elaborates rather than contradicts. Consider going further: a
`Replay` that also stubs tools from the recorded `ToolResultPart`s would make
the original claim true, and the transcript already contains the results. That
is a real feature suggestion, not just a wording one — and it is what would make
"a session that hit a bug becomes a regression test" hold for a bug in a *tool*.

## 3. `nextOutputPath` can hand a transcript someone else's output

**Severity: medium (silent wrong data), scope: one line.**

`truncate.ts`:

```ts
let counter = 0
export const nextOutputPath = (): string =>
  `${OUTPUT_DIR}/tool_${String(++counter).padStart(4, "0")}`
```

The comment acknowledges half of it — *"names restart when the process does,
which means a later run can overwrite an earlier run's file"* — and argues these
files exist to be read back within the session that produced them.

Two things that argument does not cover:

- **The counter is module-global, and the toolkit is explicitly process-wide.**
  The lock registry's own comment says the guarantee holds *"across every
  toolkit instance in the process, not merely within one"*. Two sessions sharing
  a workspace therefore interleave counters — fine — but a **restarted** process
  reissues `tool_0001` while session A's transcript still names it.
- **Exports leave the process.** `plan-snapshot-export.md` §7 already flags that
  an export carries the *reference* and not the file. Combined with a reused
  name, a restored transcript does not point at a missing file — it points at a
  **different file that exists**, which is worse. A model reading it gets
  plausible, wrong output.

**Suggested fix.** Include a per-process component:
`tool_${processId}_${counter}`, where `processId` is a short random string made
once at module load. Ascending order within a run is preserved, collisions
across runs are not possible, and it costs one line. Alternatively scope the
directory per session, which also makes cleanup obvious.

## 4. A turn that fails to capture is visible only in a log line

**Severity: low-medium, scope: one counter.**

`SessionTree`'s auto-capture swallows storage failures deliberately, and the
reasoning is right and well written:

> This runs under the event bus's publish permit, so raising would fail the
> *emit* — an unwritable disk would stop the agent mid-turn … The turn goes
> uncaptured instead: rewind cannot reach it, which is a real loss and the
> lesser one.

I agree with the choice. The gap is what is left behind: a single
`Effect.logError`. A user whose rewind cannot reach yesterday afternoon has no
way to find out why except log archaeology, and nothing aggregates it.

This compounds with pass two's finding. There are now **two independent ways for
the tree to be quietly incomplete** — a capture that failed, and a concurrent
`put` whose child was lost from the index — and both are invisible except in
logs.

**Suggested fix.** A counter, using the instruments A-2 added:
`agent_tree_capture_failures`, attributed by session. Three lines, and "why can
I not rewind to that turn" becomes a query instead of an investigation. The
same argument that justified `agent_data_dropped_events` in `/data` applies
exactly: *the drop stays non-fatal, but it is no longer invisible*.

## 5. `tail`'s UTF-8 repair is correct and has never been run on a multibyte character

**Severity: low (missing test only — I verified the code is right).**

`truncate.tail` walks forward off UTF-8 continuation bytes when a single line
exceeds the byte budget, so a cut never lands mid-character. It is the most
delicate line in the file.

Neither `CodingToolkit.test.ts` nor `CodingPrompts.test.ts` contains a single
non-ASCII character. Every `tail` test uses `"a".repeat(...)` and `"aa\nbb\ncc"`,
where the repair is unreachable — every byte is a character boundary.

I probed it rather than assume: a 100-emoji line truncated to 51 bytes (not a
multiple of 4), and a mixed `"aaa…é日🙂"` line cut at 13. **Both produced valid
text with no replacement character.** The code is right.

**Suggested test**, since the probe already exists in this report's history:
assert `tail("🙂".repeat(100), 10, 51).text` contains no `�` and decodes to
whole characters. Without it, a future refactor of the byte accounting has
nothing to fail against, and the symptom — mojibake in a model's view of command
output — is one nobody will trace back here.

## Not findings

**Capture's error handling is right, not merely defensible.** Choosing an
uncaptured turn over a dead agent is correct, and the comment argues it properly.
Finding 4 is about observability, not the decision.

**`Replay`'s limit is documented**, which is why finding 2 is about a
contradiction rather than an omission. Contrast pass three's export finding,
where the caveat was absent entirely.

**The web fetch guard and the replacer chain** were reviewed in passes two and
three and are unchanged.

## Suggested order

1. **Regenerate `STATUS.md`, and stop hand-maintaining the numbers** (1).
2. **Make `nextOutputPath` collision-free** (3) — one line, and it prevents a
   restored transcript pointing at a plausible wrong file.
3. **Fix `Replay`'s contradicting sentence** (2), and consider whether stubbing
   tools from recorded results is the feature that makes the claim true.
4. **Add the capture-failure counter** (4) and **the multibyte `tail` test** (5).

## Five passes in

The findings have moved steadily outward: correctness, then concurrency, then
adversarial input, then shape, and now the documentation and the failure paths.
That progression is itself the useful signal — the core is solid enough that
five passes have not found a defect in the agent kernel, and what they keep
finding is at the edges: the scaffolding, the records, and what happens when
something that is allowed to fail does.
